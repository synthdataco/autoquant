# Platform & Benchmark Suggestions (campaign-6)

## `[ergonomics] Starter agent/predict.py writes one JSON file per prompt and runs single-threaded scoring`
- **What happened**: The starter `agent/predict.py` serializes each prompt's 1,000 paths to an individual `.json` file (`json.dumps`) and invokes `synth_lib.backtester.orchestration.backtest()` with `scoring_executor=None`. On a 10-day `CRYPTO_1H` evaluation (1,440 prompts per asset × 5 assets = 7,200 prompts), writing 7,200 JSON files and scoring them single-threaded takes over 12 minutes per window, whereas `synth_lib.benchmark.generate_predictions` already supports memory-mapped daily `float32` `.npy` files (`day_files`) and `backtest()` already accepts a `ProcessPoolExecutor`.
- **What would fix it**: Have the starter `agent/predict.py` write daily `float32` `.npy` + `.json` index files via `day_files` (matching `synth_lib.benchmark.generate_predictions` and the verdict runner's `float32` precision) and pass `scoring_executor=ProcessPoolExecutor(max_workers=...)` to `backtest()`, plus an optional `--competition` flag to evaluate all assets in `CRYPTO_24H`, `COM_EQU_24H`, or `CRYPTO_1H` in one command.

## `[synth-lib] Add a skip_smoothed_scores=True option to synth_lib.backtester.orchestration.backtest()`
- **What happened**: Inside `backtest()`, scoring 1,440 `CRYPTO_1H` prompts with a 12-worker `ProcessPoolExecutor` takes only ~10 seconds, but `calculate_smoothed_scores()` then spends ~73 seconds per asset looping over ~1,350 historical reward rounds to compute moving-average leaderboard scores. Since `CAMPAIGN.md` explicitly instructs agents to optimize `mean_crps` rather than field-relative smoothed scores, 85% of `backtest()` runtime on `CRYPTO_1H` is spent computing a quantity that should not be used for model selection.
- **What would fix it**: Add a `compute_smoothed: bool = True` parameter to `backtest()` (and a `--skip-smoothed` flag in `agent/predict.py`) so CRPS-only backtests skip `calculate_smoothed_scores()` and return in ~12s per asset instead of ~85s.

## `[ergonomics] Starter context slice in agent/predict.py differs slightly from synth_lib.benchmark.generate_predictions`
- **What happened**: In the starter `agent/predict.py`, the context slice is `prices.loc[: context_end(t, time_length)][-CONTEXT_MINUTES:]` (which takes `10,080` rows ending at `context_end`), whereas `synth_lib.benchmark.generate_predictions` (used by `run_verdict.py`) slices `price_frame.loc[t - pd.Timedelta(minutes=CONTEXT_MINUTES) : context_end(t, time_length, issuance_lead)]` (which starts at `t - 7d` and has `10,078` or `10,079` rows).
- **What would fix it**: Use the exact same slice `prices.loc[t - pd.Timedelta(minutes=CONTEXT_MINUTES) : context_end(t, time_length)]` in `agent/predict.py` so local evaluation and verdict evaluation pass identical DataFrames to `simulate()`.

## `[synth-lib] load_simulate() in synth_lib/benchmark/generate_predictions.py does not add modeling_path.parent to sys.path`
- **What happened**: `load_simulate(modeling_path)` loads `agent/modeling.py` via `importlib.util.spec_from_file_location` without inserting `str(modeling_path.parent)` into `sys.path`. If an agent splits helper modules into `agent/helpers.py` and writes `import helpers` inside `agent/modeling.py`, it works when running `uv run agent/predict.py` (which adds `AGENT_DIR` to `sys.path`), but would fail with `ModuleNotFoundError` when `generate_predictions.py` is invoked from the workspace root during final verdict evaluation.
- **What would fix it**: Either temporarily insert `str(modeling_path.parent)` into `sys.path` inside `load_simulate()`, or note in `CAMPAIGN.md` that `agent/modeling.py` must be a single self-contained file or resolve sibling imports via `Path(__file__).resolve().parent`.

## `[docs] Document the Pandas 2.3+ Timestamp.as_unit('us').value vs DatetimeIndex.as_unit('us').asi8 trap`
- **What happened**: All parquet timestamps in `market_data/` use `timestamp[us, tz=UTC]`. In Pandas 2.3+, `DatetimeIndex.as_unit("us").asi8` returns int64 microseconds as expected, but calling `pd.Timestamp(start_time).as_unit("us").value` still returns **nanoseconds** (`1000x` larger!). Mixing `context_prices.index.as_unit("us").asi8` with `pd.Timestamp(start_time).as_unit("us").value` silently shifts `start_time` by `1000x` unless `int(round(t.timestamp() * 1_000_000))` or `t.value // 1000` is used.
- **What would fix it**: Add a one-line note in `DATA.md` under the `timestamp[us, tz=UTC]` bullet warning that scalar `pd.Timestamp.value` is always nanoseconds in Pandas 2.x even after `.as_unit("us")`.
